# Проверка реального канала и исправления 0.2.0-rc.2

Дата: 8–9 ноября 2026 года. Клиент — физический Ethernet домашнего ПК в РФ;
выделенный сервер — Нидерланды. Производственные ноды не использовались для
итоговой матрицы. Первоначальные незавершённые замеры на другом сервере хранятся отдельно.

## Исходная 0.2.0-rc.1

Полная таблица: [260 строк CSV](data/real-channel-20261108.csv),
[число строк и SHA256 источников](data/real-channel-20261108-manifest.json).
Нулевые, неудачные и idle-попытки сохранены. Это описательные результаты одного
изменчивого канала, а не доказательство универсального выигрыша.

| Набор | Прогоны | Условия |
|---|---:|---|
| XHTTP REALITY H2, нагрузка | 80 | A/B/C/D × solo/rival/own4/upload × 5 × 30 с |
| XHTTP idle | 20 | По 5 независимых процессов клиента на вариант, 600 с |
| Hysteria UDP443 | 10 | A/C solo, данные не пошли; другие сценарии не измерялись |
| RAW REALITY без Vision | 100 | 80 нагрузочных и 20 idle-попыток |
| Hysteria UDP8443 | 50 | A/C, четыре нагрузки и idle, по 5 повторов |

A — официальный Xray v26.10.31; B — rc.1 flow off; C — rc.1 flow on;
D — rc.1 flow on + compete. Официальный Windows-клиент одинаков для всех вариантов.
Серверные журналы подтвердили источник data plane, совпадающий с прямым SSH
через физический интерфейс. IP-адреса и ключи в публичную таблицу не включены.

Пример XHTTP, медианы пяти прогонов, значения в таблице округлены только для чтения:

| Сценарий | A, Мбит/с | C, Мбит/с | A, p95 мс | C, p95 мс |
|---|---:|---:|---:|---:|
| solo download | 212,06 | 179,48 | 247,3 | 256,7 |
| rival download | 105,17 | 105,20 | 515,6 | 320,8 |
| own4 download | 227,99 | 250,21 | 1786,6 | 603,8 |
| upload | 34,73 | 37,94 | 460,9 | 161,7 |

p95 — сначала внутри прогона по успешным запросам, затем медиана пяти p95.
Поля CSV `rtt_*` содержат полную задержку HTTP probe через прокси, а не ICMP RTT.
Ошибки запросов отдельно сохранены в notes; условный p95 нельзя читать без них.
В XHTTP были два промежутка без байт дольше двух секунд и ни одного учтённого
обрыва bulk-потока. Улучшение задержки видно в части сценариев, но общего
преимущества по скорости нет. Прямая базовая линия заметно менялась между этапами.

Upload посчитан по байтам, полученным приложением на сервере, а не только
переданным локальному сокету. CPU процесса: 100% соответствует одному ядру;
его фактическое окно измерения указано в notes и может включать завершение
последних probes после 30 секунд нагрузки. `server_mbit` — счётчик всего
интерфейса, включая контроль SSH и конкурента, а не только полезные данные Xray.

На RAW без Vision большинство коротких запросов не прошло, многие bulk-прогоны
дали ноль. По этим данным нельзя определить причину: сбой пути, конфигурация,
поведение сервера и фильтрация остаются версиями. Успешные p95 здесь особенно
нерепрезентативны. Нужен отдельный контроль RAW с Vision.

UDP echo: на 443 — 0/3 ответа, на 8443 — 3/3. Hysteria на 8443 передавала данные:
медианы solo download A/C — 255,43/255,93 Мбит/с. У A были stalls/ошибки в
скачивании, у C — неудача в upload. Это не доказывает безусловную стабильность
одной из сборок и не локализует причину недоступности UDP443.

## Ограничение первоначального idle

Штатная `ConnectionIdle` в закреплённом upstream равна 300 секундам.
Логическое TCP-соединение после 600 секунд может закрыться при исправном
транспортном keepalive. Поэтому первоначальный idle проверяет поведение
конфигурации по умолчанию, но не изолирует keepalive QUIC.
У XHTTP и RAW часть начальных запросов вообще не установилась за 5 секунд:
такие попытки помечены `idle_valid=false`, их нельзя считать выдержанным idle.
В notes отдельно указаны начальный запрос, старое соединение и восстановление.
Пять idle-повторов одного варианта шли параллельно в отдельных процессах;
это не пять независимых временных окон.

## Исправления

1. В compete PI увеличивал окно при распознанной чужой очереди, после чего
   дополнительная ветка governor немедленно уменьшала его на четверть.
   Регрессионный тест полного цикла воспроизводит застревание на 65535 байтах
   на rc.1 и проходит с исправлением. Дополнительное уменьшение пропускается
   только при активной конкуренции и чужой очереди; тесты собственной очереди,
   отключённого режима и соседней закачки сохраняют уменьшение.
2. TLS reload/OCSP публикует новые неизменяемые сертификаты через atomic slots;
   незавершённая замена cert/key оставляет последнюю валидную пару. Исходный
   protobuf-конфиг и опубликованный сертификат не меняются. Кэш выдачи CA
   отделён от общего `tls.Config`. Прямой вызов `BuildCertificates` теперь
   возвращает снимок; live reload сервера осуществляется через `GetTLSConfig`.
3. Гонка флага закрытия в QUIC-тесте заменена синхронизацией каналом.
   Та же гонка воспроизведена на чистом закреплённом upstream.

Выбор immutable snapshots соответствует контракту
[Go crypto/tls.Config](https://pkg.go.dev/crypto/tls#Config): используемую
конфигурацию нельзя менять параллельно с handshake. При проектировании
контроля полосы учтены ограничения таймеров и TSQ из
[руководства tc-netem](https://man7.org/linux/man-pages/man8/tc-netem.8.html).
Это основания методики, а не доказательство причин прежнего завышения полосы.

## Повторная матрица rc.2

Завершены 80 XHTTP и 20 дополнительных RAW/Vision прогонов, по 5 × 30 секунд
на ячейку. Клиент тот же официальный; A — stock, C — rc.2 flow on,
D — rc.2 compete, E — rc.1 compete. Медианы XHTTP, Мбит/с:

| Сценарий | A | C | D | E |
|---|---:|---:|---:|---:|
| solo download | 150,41 | 190,98 | 124,81 | 146,16 |
| rival download | 102,47 | 44,96 | 103,99 | 69,64 |
| own4 download | 258,61 | 241,87 | 246,85 | 250,18 |
| upload | 100,30 | 189,70 | 138,69 | 164,26 |

Все 110 повторных строк, включая отдельный idle:
[CSV](data/real-channel-20261109.csv), [SHA256 источников](data/real-channel-20261109-manifest.json).

Восемь из 80 ячеек XHTTP дали нулевую передачу: у C — три, D — две,
E — три, у A — ни одной. Эти нули включены в медианы. В коротких smoke
были неудачи и у A. Поэтому различие нельзя автоматически приписать только
патчу или только пути. В rival C теряет полосу, D приблизился к stock;
в других сценариях результат меняется. Общего выигрыша сборки эти данные
не доказывают. Медианы p95 соседнего запроса в rival A/C/D/E:
444,17/329,23/335,21/365,19 мс. Это p95 только успешных запросов; ошибок
у A/C/D/E было 0/96/0/120 из 600 запросов на вариант.

В RAW/Vision 17 из 20 попыток дали ноль; в трёх были данные, но медианы
всех четырёх ячеек равны нулю. Это подтверждает проблему данного опыта,
а не устанавливает её причину. TLS-соединение сервера с целью REALITY
проверено успешно; в части клиентских TCP-сокетов наблюдались только
1452 принятых байта и повторные FIN. Локализация сбоя на пути не выполнена.

Опыт выполнялся с двумя согласованными паузами. Незавершённый завершающий
iperf upload при второй паузе отмечен как прерванный, его итог неизвестен.
После продолжения завершённые ячейки не повторялись; исходные данные и
метаданные предыдущих этапов сохранены.

## Hysteria после десяти минут простоя

На UDP8443 при `connIdle=1800` на обеих сторонах все пять начальных соединений
у A и C установились. После 600 секунд C сохранил 5/5 логических соединений,
A — 0/5; все пять A восстановились новым запросом. Медиана времени запроса
после простоя: C — 71,59 мс, A с восстановлением — 447,72 мс.
Это подтверждённый результат серверного keepalive на проверенном пути.
Пять соединений одного варианта ожидали одновременно в отдельных процессах;
это не пять независимых десятиминутных временных окон. Keepalive уже входил
в предыдущую версию форка, а не добавлен текущим исправлением TLS.

## Проверки и оставшаяся работа

- Полный Linux `go test -vet=off -tags=http2legacy -count=1 ./...` прошёл после
  загрузки geodata. Первое падение без `geoip.dat`/`geosite.dat` сохранено.
- Целевые regression/race-тесты controller, TLS reload/CA и QUIC прошли.
- Общий race-прогон splithttp завершился `signal: killed`; журнал ядра подтвердил
  global OOM. Сервер имеет 961 МиБ RAM и 511 МиБ swap. Раздельно прошли 205 из
  206 тестов; `TestH2WindowsEndToEnd` первоначально завершился кодом 137.
  Повтор с дополнительным временным swap прошёл без уменьшения нагрузки.
  Все 206 тестов прошли раздельно, также прошли seed-корпусы fuzz под race.
  Это не успешный запуск всей splithttp suite одним процессом: исходный OOM сохранён.
- `go vet` выявил прежние копирования protobuf mutex в XMUX. Эти предупреждения
  не исправлены в рамках текущих изменений.
- Семь локальных Python-тестов release/export прошли; итоговый патч применился
  на чистую закреплённую базу.
- `build.py prepare`, расширенные проверки и обе сборки rc.2 Linux/Windows прошли.
- После возобновления завершены все 40 warm-rival и 20 cold-rival ячеек;
  каждый конкурент проверен по активности и полученным байтам. Данные:
  [полные строки](data/rc2-netem-results.jsonl), [сводка](data/rc2-netem-summary.json),
  [SHA256 и epochs](data/rc2-netem-manifest.json). Сохранены исходные 25 строк до паузы.
  Устойчивого прироста от compete-фикса стенд не подтвердил: cold20 rc.1/rc.2
  1,11/1,17 Мбит/с, cold100 — 21,36/16,27 Мбит/с (медианы пяти прогонов).
- После продолжения завершены smoke, обе нагрузочные матрицы rc.2 и отдельный idle Hysteria.
- Docker-образ на Node 3.4.4 собран, ядро запускается под s6 через mTLS/JWT API.
  В контроле с двумя настроенными пользователями прошли: лимит двух соединений
  (третье отклонено), лимит download 20 Мбит/с (20,45/20,46/20,40 за три 10-секундных
  опыта), сохранение передачи при remove/add того же ключа, отзыв, смена ключа,
  метрики и остановка. При grace=2 передача прекратилась через 2,00 с, при смене
  ключа — практически сразу; EOF пришёл через 3,02/1,02 с соответственно.
  При drain=3 данные шли 2,99 с, EOF — через 4,03 с. Второй пользователь не подключался.
  Это локальный канал данных с настоящим Node API, а не полноценный запуск панели.
  [Сводка проверок и digest образа](data/rc2-validation.json).

## Обнаруженное ограничение Node 3.4.4

В отдельном опыте с **единственным** пользователем его remove/add-синхронизация
сохранила текущую передачу, но последующее постоянное удаление через Node API
вернуло success без остановки передачи. В версии 3.4.4 удаление последнего
пользователя очищает `xtlsConfigInbounds`, а `addUserToInbound` не восстанавливает
этот список; следующий remove заканчивается раньше обращения к Xray.
Это воспроизведено и согласуется с
[исходником Node 3.4.4](https://github.com/remnawave/node/blob/3.4.4/src/modules/internal/internal.service.ts#L152-L208).
Двухпользовательский контроль выше изолирует работу Xray от этого дефекта.
**Node в образе не исправлялся; нельзя считать последний пользовательский сценарий пройденным.**
Первые ошибки проверяющего скрипта (ожидание HTTP 200 вместо успешного 201,
неучтённая ещё закрывающаяся TCP-сессия) также сохранены отдельно.

Сырые JSONL, baseline до/после, журналы, версии, конфиги без секретов и скрипты
сохранены локально в каталогах `reports/real-channel-20261108-*` и `20261109-*`.
Их неудачи не удалялись. Проверка браузерных страниц/видео, настоящего доменного
TLS и полноценной связки тестовой панели с Node ещё не выполнена.
Изменения остаются в отдельной локальной ветке, публикации и установки на прод нет.
